Phạm vi và topology

Đóng gói ứng dụng cho Linux amd64, VPS Ubuntu 24.04 (6 vCPU, 16 GB RAM), K3s và Argo CD; origin công khai https://label-x.williamtrinh.online. Các file được phát triển trên develop; phát hành theo commit đã được đưa vào main qua quy trình hiện hành. Tài liệu này không cấp quyền triển khai, thay secret, tự merge hoặc tự push.

Image backend cũng chạy CPU Celery worker, một beat và migration job bằng cách đổi command. PostgreSQL, Redis, Object Storage, CVAT và GPU detector là các dịch vụ ngoài. Không cài CUDA/torch, không build GPU worker và không đóng gói checkpoint hay dataset.

Hai Dockerfile dùng context riêng trong src/frontend và src/backend, với allowlist .dockerignore. Base Node 22, Python 3.12 và uv được pin bằng digest; dùng npm ci và uv sync --locked --no-dev. Runtime frontend chỉ lấy standalone, public assets và .next/static; runtime backend không có uv hoặc dependency dev. Khi nâng base image, cập nhật cả tag lẫn digest và chạy lại smoke test.

Build và smoke test cục bộ

Chạy từ root repository trên Linux/WSL có Docker Engine và Buildx. Không cần secret production hoặc dịch vụ đang chạy của máy. Build cần truy cập Docker Hub, GHCR (uv), npm, PyPI và Google Fonts; font được Next nhúng vào bản build, không tải từ Google khi người dùng mở trang.

docker buildx build --load --platform linux/amd64 \
  -t labelx-backend:production-local -f src/backend/Dockerfile src/backend
docker buildx build --load --platform linux/amd64 \
  -t labelx-frontend:production-local -f src/frontend/Dockerfile src/frontend
python3 scripts/containers/smoke.py \
  --backend labelx-backend:production-local \
  --frontend labelx-frontend:production-local

Script tạo network, PostgreSQL và Redis riêng với tên ngẫu nhiên; không mở port ra host. Nó kiểm tra user không root, amd64, không mang env/model/dev dependency; chạy migration bằng owner, tạo role runtime hạn chế audit, chạy Gunicorn, static admin, CPU worker ping và beat. Frontend chạy với proxy target khác build/default để chứng minh đổi target ở runtime; kiểm tra trang login, Next assets, logo, CSRF cookie, slash API, static/admin và chặn mock auth. Tất cả container, volume tạm và network do script tạo được dọn trong finally; image build được giữ lại.

Smoke không xác nhận GPU/model, CVAT, S3 thật, TLS/Ingress, resource sizing hoặc nghiệm thu chất lượng MVP. Thư mục fixtures/data/model trên máy không phải build input.

Backend: runtime configuration

Image đặt DJANGO_SETTINGS_MODULE=config.production, bắt buộc debug tắt và allowed hosts tường minh. Dùng Kubernetes Secret/ConfigMap hoặc env file ở ngoài repo; không truyền secret qua build argument. API, CPU worker và beat phải dùng cùng secret để giải mã credential VLM/GPU đã lưu trong DB.

Backend phải là Service nội bộ. Cấu hình này tin X-Forwarded-Proto từ proxy: Ingress ở ranh giới công khai phải ghi đè header của client, không cho người ngoài truy cập Pod/API trực tiếp. Không rewrite cookie sang domain của Service. Dùng TLS cho domain, thiết lập timeout/giới hạn body của Ingress đồng bộ với proxy và Gunicorn.

Chạy thủ công với image đã build

Ví dụ sau chỉ là lệnh tham khảo, cần network và env file do vận hành chuẩn bị. Env runtime dùng DB role hạn chế; env migration dùng owner. Env file nằm ngoài repository và không được commit.

docker run --rm --network labelx --env-file /secure/labelx-migration.env \
  labelx-backend:production-local python manage.py migrate --noinput

# Chạy bằng owner một lần để cấp role runtime đúng quyền audit.
docker run --rm --network labelx --env-file /secure/labelx-migration.env \
  labelx-backend:production-local python manage.py provision_runtime_db_role \
  labelx_runtime --password-env RUNTIME_DB_PASSWORD

docker run --rm --network labelx --env-file /secure/labelx-backend.env \
  --name labelx-backend labelx-backend:production-local
docker run --rm --network labelx --env-file /secure/labelx-backend.env \
  labelx-backend:production-local celery -A config worker -l INFO \
  --concurrency=2 --max-tasks-per-child=20 --max-memory-per-child=393216
docker run --rm --network labelx --env-file /secure/labelx-backend.env \
  labelx-backend:production-local celery -A config beat -l INFO \
  --pidfile=/tmp/celerybeat.pid --schedule=/tmp/celerybeat-schedule
docker run --rm --network labelx -p 127.0.0.1:3000:3000 \
  -e LABELX_API_PROXY_TARGET=http://labelx-backend:8000 \
  labelx-frontend:production-local

Chỉ một beat chạy tại một thời điểm; khi rollout dùng strategy Recreate hoặc cơ chế leader được duyệt. Với image backend không có ENTRYPOINT đặc biệt, command được thay thế trực tiếp. Không tự migrate khi khởi động API/worker.

CI, publish GHCR và promotion

  1. .github/workflows/ci.yml giữ nguyên các kiểm tra Windows/framework/backend/detector/frontend. Job production-images phụ thuộc đủ 5 job, build cả hai image amd64 rồi smoke. Develop, PR và main đều chỉ build/test ở workflow này; token chỉ có contents: read.
  2. production-images.yml nhận workflow_run khi CI hoặc Phase Testing hoàn thành trên main, hoặc dispatch thủ công trên main với full commit_sha. Workflow file cần có trên default branch để GitHub phát sự kiện; default branch có thể là develop. Source commit phải đã là tổ tiên của main.
  3. Job gate không có quyền ghi package. Nó kiểm metadata repo/branch/event/path/SHA và các job bắt buộc của cả hai upstream run mới nhất. PR, fork, develop, run sai SHA, job skipped/failed hoặc thiếu build-smoke đều không đủ điều kiện.
  4. Tải phase-evidence-<SHA> từ run đã xác minh và gọi nguyên gate quality-gate.cjs verify-suite trên test plan của cùng commit; kiểm mọi phase MVP, case ID, checksum plan/JUnit và không skip. Nếu chưa có run thành công thì ghi đang chờ, không publish. Thiếu/expired artifact hoặc suite không đủ sẽ chặn workflow.
  5. Chỉ sau gate mới cấp packages: write cho job publish. Build hoặc pull lại digest của tag đã có, smoke đúng hai image, rồi push tag mới sha-<full-40-character-SHA>. Không dùng latest hoặc tag nhánh. Rerun tái sử dụng digest của SHA đã publish thay vì ghi đè. Người có quyền registry vẫn có thể sửa tag ngoài workflow; Kubernetes phải pin digest.
  6. Workflow summary và artifact image-digests-<SHA>/image-digests.json ghi hai tên/tag/digest/reference, source SHA, CI run ID, test run ID và publish run ID. Hai lần push registry không phải giao dịch nguyên tử; nếu một image push lỗi, workflow thất bại và rerun giữ image đã có rồi hoàn tất image còn lại.

Kế hoạch kiểm thử hiện có còn các case planned. Khi gate MVP chưa có bằng chứng đầy đủ, image phát hành sẽ chưa được publish; không thay test plan hoặc đánh dấu skip để vượt gate. Có thể build/test image local và trên develop/PR trong lúc hoàn thiện MVP.

Publish image không phải promote production. cd.yml vẫn yêu cầu trusted main CI + MVP cùng SHA, environment protection, staging thành công đúng CI/test run trước production, target hooks và LABELX_CD_ENABLED. Tính năng này không bật CD, không sửa workflow phase-testing/cd và không thêm deploy hook. Khi vận hành tích hợp GitOps, phải nối receipt digest vào các hook được duyệt; không để Argo CD tự theo tag mutable hoặc tự sync một thay đổi image trước staging/approval. Phải dùng cùng cặp digest đã qua staging khi promote.

Luồng develop → main → GitOps

  1. Hoàn thiện thay đổi trên nhánh task xuất phát từ develop, chạy kiểm tra, commit và push nhánh nguồn (ví dụ codex/production-images). Mở PR nhánh task → develop, chờ CI và review; PO merge theo ruleset. Develop được bảo vệ: không push trực tiếp, không bỏ qua status checks.
  2. Chỉ sau khi PR task đã được review và PO merge vào develop mới mở PR develop → main. Chờ CI và review toàn bộ luồng; PO merge bằng merge commit. Agent không tự merge hoặc push trực tiếp main.
  3. Commit main có SHA riêng sau merge. Chạy CI và Phase Testing MVP cho chính SHA đó; workflow publish chỉ phát hành sau khi hai gate thành công. Lấy cặp digest từ summary hoặc artifact image-digests-<MAIN_SHA>.
  4. Publish mới chỉ tạo image trên GHCR. Argo CD không tự đổi ứng dụng khi registry có tag SHA mới. Cần một thay đổi GitOps riêng, cập nhật trường image: trong manifests hoặc giá trị Helm/Kustomize sang tag sha-<MAIN_SHA> hay, ưu tiên, @sha256:... từ receipt.
  5. Đưa thay đổi manifests qua CI/review và gate staging/production hiện có, giữ đúng cặp digest đã kiểm ở staging. Khi commit manifests được phê duyệt vào nhánh/path Argo CD theo dõi, Argo CD mới sync theo chính sách ứng dụng. Nếu automated sync đang bật, thời điểm merge manifests chính là điểm kích hoạt triển khai nên phải nằm sau approval.

Phạm vi thay đổi này dừng ở images, kiểm chứng và pipeline publish. Không tạo/sửa manifests thực tế, Argo Application, deploy hook hoặc secret; bước GitOps cần được tích hợp và phê duyệt riêng.

Cấu hình GitHub và visibility package

  1. Review các thay đổi, đưa develop vào main theo quy trình hiện tại. Bổ sung status production-images vào branch protection/ruleset cùng các check đang có; không gỡ check cũ.
  2. GitHub Actions phải được policy repo/organization cho phép cấp packages: write cho job publish. Dùng GITHUB_TOKEN tự cấp, không cần thêm PAT push vào secret repository. Các action mới được pin commit SHA; kiểm allowlist Actions nếu organization có giới hạn.
  3. Nếu package đã tồn tại, trong Package settings → Manage Actions access, cấp repo toilatrung/label-x quyền ghi; kiểm linked repository/inherit access. Label OCI org.opencontainers.image.source hỗ trợ liên kết source. Publish/đọc package API có thể bị chặn nếu package chưa cấp quyền.
  4. Sau lần publish đầu, kiểm riêng hai package labelx-frontend và labelx-backend. Package mới mặc định private; repo public không làm package public. Nếu cho phép tải ẩn danh, đổi Package settings → Change visibility → Public theo quyết định vận hành. Thử anonymous pull từ môi trường sạch bằng digest.
  5. Nếu giữ private, dùng PAT classic chỉ read:packages của tài khoản có quyền đọc (và SSO khi cần) để tạo kubernetes.io/dockerconfigjson Secret trong đúng namespace của workload. Không dùng token packages:write cho K3s. Truyền authfile qua secret store/vận hành, không commit token hoặc authfile vào Git.
  6. Giữ runner/environment labelx-evaluation, policy dữ liệu/model và staging/production protection đang có. Việc thiết lập/nâng trạng thái MVP, secrets và deploy hooks phải thực hiện ở bước vận hành được phê duyệt riêng.
# Ví dụ tạo secret từ Docker config đã đăng nhập bằng tài khoản chỉ đọc.
# Authfile /secure/ghcr-readonly/config.json do vận hành cung cấp; không nằm trong repo.
kubectl -n labelx create secret generic ghcr-pull \
  --type=kubernetes.io/dockerconfigjson \
  --from-file=.dockerconfigjson=/secure/ghcr-readonly/config.json

Dùng image trong K3s / Argo CD

Đoạn cấu hình tham khảo; chưa apply hay tạo Argo Application. Thay FRONTEND_DIGEST và BACKEND_DIGEST bằng giá trị sha256:... trong cùng receipt. Secret/ConfigMap, Service nội bộ, TLS Ingress, PostgreSQL, Redis, Object Storage, manifest GPU và NetworkPolicy phải được chuẩn bị ngoài image. Argo CD dùng manifest được duyệt trên main; Git credentials của Argo CD không thay cho imagePullSecret của kubelet.

apiVersion: apps/v1
kind: Deployment
metadata:
  name: labelx-backend
spec:
  replicas: 1
  selector:
    matchLabels: {app: labelx-backend}
  template:
    metadata:
      labels: {app: labelx-backend}
    spec:
      imagePullSecrets: [{name: ghcr-pull}]  # bỏ khi cả hai package public
      securityContext: {runAsNonRoot: true, runAsUser: 10001, runAsGroup: 10001}
      containers:
        - name: api
          image: ghcr.io/toilatrung/labelx-backend@BACKEND_DIGEST
          ports: [{containerPort: 8000}]
          envFrom:
            - configMapRef: {name: labelx-runtime}
            - secretRef: {name: labelx-runtime-secrets}
          resources:
            requests: {cpu: 500m, memory: 512Mi}
            limits: {cpu: "2", memory: 2Gi}
          securityContext:
            allowPrivilegeEscalation: false
            readOnlyRootFilesystem: true
            capabilities: {drop: [ALL]}
          volumeMounts: [{name: tmp, mountPath: /tmp}]
          startupProbe: {httpGet: {path: /healthz/, port: 8000}, failureThreshold: 30, periodSeconds: 2}
          livenessProbe: {httpGet: {path: /healthz/, port: 8000}, periodSeconds: 15}
      volumes: [{name: tmp, emptyDir: {}}]
---
apiVersion: batch/v1
kind: Job
metadata:
  name: labelx-migrate-RELEASE_ID
  annotations:
    argocd.argoproj.io/hook: PreSync
    argocd.argoproj.io/hook-delete-policy: BeforeHookCreation,HookSucceeded
spec:
  backoffLimit: 1
  template:
    spec:
      restartPolicy: Never
      imagePullSecrets: [{name: ghcr-pull}]

Secret migration chứa DB owner; sau migrate phải cấp quyền cho runtime role với provision_runtime_db_role theo quy trình đã có. Migration PreSync là việc vận hành tích hợp trong tương lai, phải nằm sau gate promote; không có hook nào được bật bởi thay đổi này.
